# Vehicle Log → LLM-Ready Data Formatter

A small pipeline that takes messy, raw vehicle telemetry data (the kind of
thing a CAN-bus / OBD-II logger produces) and turns it into clean,
structured data formatted for ingestion by an LLM — with the goal of
supporting automated fault diagnosis or maintenance-report generation.

I built this to sharpen a specific skill: **formatting real-world data for
LLM ingestion**, not just cleaning it. Cleaning gets data correct; LLM
formatting gets it *usable* — unambiguous, appropriately chunked, and
sized to fit a context window without wasting tokens on redundant
steady-state data.

## Why this isn't just "CSV to JSON"

1. **Raw sensor logs are dirty.** Real loggers produce missing fields,
   duplicate timestamps, and sensor glitches constantly. Feeding that noise
   directly into a prompt wastes tokens and risks the model treating a
   glitch as a real signal.
2. **LLMs parse explicit structure far more reliably than raw tables.**
   Column-aligned CSV text forces a model to infer meaning; labeled JSON
   key/value pairs remove that ambiguity.
3. **Context windows are finite and token cost is real.** Instead of
   dumping every row into a prompt, this pipeline chunks data around
   *events* (fault codes) with a short window of surrounding context —
   similar to the chunking strategy used in retrieval-augmented generation
   (RAG) systems.
4. **Compact statistics beat verbose tables.** Rather than repeating every
   raw row, the pipeline computes rolling min/avg/max per sensor around
   each event — cheaper in tokens, easier for a model to reason over.

## Pipeline

```
data/generate_sample_log.py   → generates a synthetic, intentionally messy
                                 vehicle telemetry CSV (no real/proprietary
                                 data used)
clean_and_format.py           → cleans the raw log (missing values,
                                 duplicate timestamps, sensor glitches,
                                 malformed codes) and extracts fault-code
                                 events as structured JSON chunks
build_prompt.py               → shows how a cleaned event chunk becomes an
                                 actual LLM prompt (no API key required to
                                 run — this prints the prompt string itself)
```

## Running it

```bash
pip install -r requirements.txt   # stdlib only, but kept for convention
python3 data/generate_sample_log.py
python3 clean_and_format.py
python3 build_prompt.py
```

## Example output

A single LLM-ready event chunk (`output/llm_ready_events.json`):

```json
{
  "event_type": "diagnostic_trouble_code",
  "dtc_code": "P0128",
  "timestamp": "2026-09-18T08:02:30",
  "reading_at_event": {
    "rpm": 3687.5,
    "throttle_pct": 56.3,
    "coolant_temp_f": 116.3,
    "vehicle_speed_mph": 85.0
  },
  "sensor_summary_before_event": { "rpm": {"avg": 3435.6, "min": 3373.1, "max": 3507.8}, "..." : "..." },
  "sensor_summary_after_event":  { "rpm": {"avg": 3418.2, "min": 3253.7, "max": 3614.7}, "..." : "..." },
  "description": "Fault code P0128 triggered at 2026-09-18T08:02:30. At the moment of the event: RPM=3687.5, throttle=56.3%, coolant temp=116.3F, speed=85.0 mph."
}
```

Every cleaning decision is logged for auditability in
`output/cleaning_report.json` — e.g. "coolant_temp_f missing at row 20;
forward-filled with 74.5" — so nothing is silently altered.

## What I'd extend this into with more time

- Real DTC code lookup (mapping P0128 → human-readable descriptions) via a
  small reference table
- Actual LLM API integration (currently `build_prompt.py` prints the
  prompt rather than calling an API, to keep this runnable without a key)
- Streaming/incremental processing for live telemetry rather than batch CSV

## Notes

All data in this repository is **synthetic**, generated by
`data/generate_sample_log.py`. No real vehicle, customer, or proprietary
data is used anywhere in this project.
